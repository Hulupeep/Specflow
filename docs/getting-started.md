# Getting started

Use [onboarding](onboarding.md) for supported host-aware setup and [README](../README.md#install-and-use) for source commands. Choose Codex or Claude Code explicitly when automatic detection is ambiguous. Installation is idempotent within its documented ownership rules; retained active runs keep their pinned runtime until a safe update boundary.

## Start with one real change

1. Supply repository, board/CLI, stack and selected work if they are not already known.
2. Give the installed loop selector the intended outcome and constraints. Use a tweak or bug path when those checks cover the risk; do not turn every ask into an epic.
3. Reuse existing research, contracts, source facts and tests. Add only applicable missing acceptance and failure cases.
4. Run the required checks against the actual path in scope. A missing backend or never-run journey remains a gap.
5. Review the evidence and current findings before the existing publication/release boundary.

Formal work follows create/refine → simulate → audit → pre-flight at the selected depth. Audit is story compliance, not build or release readiness. See [how it works](how-it-works.md), [work routing](should-i-use-specflow.md) and the [installed specification policy](../templates/SPECIFICATION.md).

## Review choices

Normal fresh same-host advisory review uses its configured runtime role. Explicit cross-family [Duo](duo-build.md) requires the other provider CLI and its authentication; GitHub reads require usable `gh` access. No missing credential or denied read can be reported as a completed independent review. TypeSafe remains optional advice.

## Check your installation and run

Use the [onboarding diagnostics](onboarding.md) for setup and the [command reference](reference.md) for actual runner/trace operations. Start a new agent session after updating skills. Do not copy credentials into issues or run artifacts, overwrite custom gates blindly, or treat an install check as product acceptance.
