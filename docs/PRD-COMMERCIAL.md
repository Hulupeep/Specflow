# Specflow: evidence for agent-built software

Commercial narrative derived from the [canonical internal PRD](PRD.md). This is positioning, not evidence of customers, revenue or completed unattended delivery.

## The problem

Coding agents can produce plausible changes and declare them complete. A team still needs to determine whether the behavior works, whether existing rules survived, and what remains unknown. More generated code does not answer those questions.

## The product

Specflow is a trust harness around the worker. Agents can research, specify and build; accepted contracts, independent verification and mechanical gates control acceptance. Capability does not create authority.

It keeps the intended outcome, checks, expected references, actual execution, findings and authorization history in durable artifacts. Reviewers can inspect the evidence rather than reconstructing a promise from a conversation. Verification effort follows risk: a small reversible change receives a lighter path than a database, billing or integrated workflow change.

## Intended commercial wedge

Agencies and consultants need a reviewable evidence packet for AI-assisted client delivery. Product teams need the same trail for brownfield changes, particularly where data, permissions, calculations or persistence matter. These are intended buyers and value hypotheses; adoption and willingness to pay require separate evidence.

A useful packet identifies what changed, what actually ran, which source/oracle supported the result, what failed or was skipped, unresolved findings, and who authorized the boundary. The aim is faster accepted value with less reconstruction, not more tickets or reviewer calls.

## Boundaries

A provider's confidence or exit code is not acceptance. Source scans do not prove runtime correctness. A screenshot cannot prove persistence or a calculation. A compliant ticket or independent model review cannot substitute for required execution. Required missing, skipped or stale evidence stays nonpassing, and an exception does not become a pass.

Existing privacy, permission, CI and release gates remain authoritative. Specflow does not supply ground truth that a project never defined, guarantee every feature safe, or silently authorize publication, merge or deployment.

## Direction and evidence

The product target is useful, explainable intent-to-evidence development with replaceable research, builder and reviewer roles, using HeyStax as the operational control plane. Research-led work enters as existing issues; Specflow strengthens the contract, builds and reports the result. The operator, provider and chat context can change while durable rules and evidence remain.

Current source contains the local harness and improvement/controller interfaces. Final released installs, real-product measurable gains and unattended end-to-end operation each need their own qualification. Repo tests and synthetic corpus receipts are engineering evidence, not customer benefit.
